4 / Full-stack implementation

A simple form.
A durable delivery path.

A contact form is part of the business’s front door. I separated saving the inquiry from delivering the notification, so an email delay does not have to become a lost conversation.

Help people explain the need

The checklist asks for goals and existing materials. Service guidance and pricing help visitors frame the conversation before they send.

Confirm what actually happened

The form distinguishes a saved inquiry from delayed delivery or a failed request. A reference number gives the submission an identity.

Make recovery part of the design

The browser reuses its submission ID on a retry. The backend stores delivery state and has separate paths for retrying and retaining failures.

From submission to notification

Cloudflare Worker / D1 / Queues / Email

    Validate the request

    Check origin, required fields, lengths, email format, and the honeypot.

  2. 2 / Persist

    Save the inquiry

    Saved response → Browser
  3. 3 / Dispatch

    Queue the delivery

    Send an inquiry ID to the queue. The consumer loads the stored record.

  4. 4 / Observe

    Send & track email

    Store the message ID, then record delivery, deferral, or failure events.

Recovery path: delayed retries for transient send errors, a scheduled job for stranded inquiries, and a dead-letter queue for terminal send failures.

Built for interruption

Delivery semantics,
retries, and recovery

Retry delays

  1. 1 min
  2. 5 min
  3. 15 min
  4. 60 min

The browser creates a UUID and retains it when a request fails. The Worker looks up that client ID before inserting another inquiry. A D1 write precedes a successful saved response; a queueing failure can therefore return “saved, delivery delayed” without asking the visitor to start again.

The consumer retries temporary send errors after 1, 5, 15, and 60 minutes. A five-minute scheduled job republishes pending or queue-failed records and queued or sending records that have stalled for more than 15 minutes. Provider acceptance and actual delivery are recorded separately, making delayed or failed delivery visible in the stored inquiry state.

Request boundaries

Validation and request boundaries

The Worker accepts JSON POST requests from allowed origins, validates required fields and lengths, and uses a hidden honeypot field to discard basic automated submissions. Prepared D1 statements bind submitted values, and HTML email content is escaped before delivery.

The email binding restricts the sending and destination addresses, keeping inquiry notifications within the business’s configured delivery path.

Build-time decisions

Static export and image-delivery tradeoffs

Next.js generates the project and service routes at build time. Project metadata comes from the same records used for presentation, while specialized components own each story’s layout. Content updates require a new build and deployment.

The export uses Next.js images with unoptimized: true, so there is no runtime image-resizing service. Source dimensions, chosen assets, CSS composition, and loading priority matter. The gallery’s filters run locally in the browser; the contact Worker remains a separately deployed service.
